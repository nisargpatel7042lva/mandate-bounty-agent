## 1. Agent Games: Wildcard requirements

- Window: 21 Oct to 19 Nov 2026. Prize pool 100,000 VFY (50k / 30k / 20k).
- Submission form (`/events/wildcard`): agent link (repo, demo, or write-up), **public HTTPS endpoint**,
  use case, build context, and optionally the zkVerify checkable claim plus a proof reference.
- Judging (no weights published): useful problem, working implementation, clear explanation,
  verifiability via zkVerify (optional plus). Entries without zkVerify remain eligible.
- Rules section 1.1: prize eligibility needs a connected GitHub account **and** a wallet on the profile
  before close; winners are verified manually.
- Rules section 1.2: an agent must be reachable at a public HTTPS endpoint with no localhost, private IPs or
  custom ports; it must respond to signed tasks within the deadline, sign responses with its HMAC secret,
  and treat task IDs as idempotency keys.
- Rules section 1.4: offline agents forfeit tasks, and services that sleep cost tasks. This confirms the always-on host.
- **Gap:** rules section 04 (Wildcard) is in the index but its body is rendered client-side and could not
  be read from the served HTML. Re-check it in a browser before submission.

## 2. Agent Games: endpoint protocol and HMAC

Documented (`/build`, `/rules` section 1.3):

- The secret is a 32-byte random value generated by the platform and shown once ("Rotate Secret" on the dashboard).
  Store it as `AGENT_GAMES_HMAC_SECRET`. Rotating it invalidates the old secret immediately.
- Inbound: compute the HMAC over the **raw request body** and compare it to `x-agent-games-signature`
  **before parsing JSON**; reject on mismatch.
- Outbound: every response carries `x-agent-games-signature` over the **raw response body**.
- Register the **full handler path** (for example `/agent`). A root that returns 404 fails preflight.
- Preflight request `{ "type": "agent-games.preflight.v1", "agent_id", "issued_at", "nonce" }`;
  the signed response must be `{ "ok": true, "protocolVersion": "v1" }`. The hard response deadline is 60 s.

**Not documented by the platform:** hash algorithm, digest encoding, `sha256=` prefix, whether the key is
the secret's text or its decoded bytes, and any timestamp or replay window. Working entrants
(zeel991/vk-sentinel, poolparty21/vfy-agent) use **HMAC-SHA256, lowercase hex digest, secret text as key**,
and accept an optional `sha256=` prefix. We implement that defensively (accept both key forms and both
header forms, mirror the inbound form on output) and confirm against a live preflight once registered.

Supported proof systems (`architecture/09-supported_proofs.md`):

| Proof type | Versions / curves | Limit |
| --- | --- | --- |
| Groth16 | BN128, BN254, BLS12-381 | 64 public inputs |
| Fflonk | BN128 | 1 public input |
| Noir UltraHonk | Noir 1.0.0-beta.14 to beta.18, bb 3.0.x | 32 public inputs |
| Noir UltraPlonk | Noir ≥ 0.31.0, bb ≤ 0.76.4 | 32 public inputs |

There is **no zkTLS verifier**.

Submission routes:

- **zkverifyjs 3.3.1** (npm `zkverifyjs`, published 2026-10-21). Example call:
  `session.verify().groth16({ library: Library.snarkjs, curve: CurveType.bn128 })`, with an optional
  `domainId` for aggregation, `registerVerificationKey`, `waitForAggregationReceipt` and
  `getAggregateStatementPath`. **It requires Node ≥ 24.22.1**, and this machine has Node 22.23.
- **Kurier** (Horizen Labs REST relayer), testnet API `https://api-testnet.kurier.xyz/api/v1`, with an API key
  from testnet.kurier.xyz. The flow is `register-vk`, then `submit-proof`, then polling `job-status`
  (`Queued → Valid → Submitted → IncludedInBlock → Finalized`, plus `AggregationPending → Aggregated` when
  a target `chainId` is set). Kurier pays fees, so we don't need to hold tVFY for submissions.
- Direct submission with Polkadot.js `submitProof`.

Testnet details:

- Network: **Volta**. RPC `wss://zkverify-volta-rpc.zkverify.io`; explorer `https://zkverify-testnet.subscan.io`.
- Token: tVFY, from faucets at zkverify-faucet.zkverify.io and faucy.com/zkverify-volta.
- EVM aggregation proxies (testnet): **Base Sepolia (84532) `0x0807C544D38aE7729f8798388d89Be6502A1e8A8`**,
  Sepolia `0xEA0A0f1EfB1088F4ff0Def03741Cb2C64F89361E`, Arbitrum Sepolia, OP Sepolia, Horizen testnet, and others.
- On-chain check: `verifyProofAggregation(domainId, aggregationId, leaf, merklePath, leafCount, index)`, where
  leaf = keccak256(PROVING_SYSTEM_ID = keccak256("groth16"), vkHash, VERSION_HASH = sha256(""), keccak256(pubs)).
  The exact pubs byte encoding is to be confirmed against a live aggregation in Phase 6.

## 4. zkTLS options

Requirement: the agent, running server-side, proves "GitHub API says PR #N in repo R is merged by U"
without revealing its token.

| Provider | Server-side (agent) | GitHub API with hidden token | Proof it produces | zkVerify-native? |
| --- | --- | --- | --- | --- |
| **Reclaim zkFetch 1.1.0** (2026-07) | yes, Node backend mode | yes: `privateOptions.headers`; regex `responseMatches` / redactions | claim (`provider`, `parameters`, `context`, `identifier`) plus attestor **ECDSA secp256k1** signatures | no |
| Primus core SDK 0.3.9 (2026-10) | yes, Node | yes (MPC-TLS or proxy mode) | attestor-signed attestation | no |
| TLSNotary (tlsn-js 0.1.0-alpha.12) | Rust prover; JS is browser/WASM | yes | notary-signed attestation; still alpha | no |
| Opacity | no: SDK is React Native / on-device (`@opacity-labs/react-native-opacity`) | user-session based | MPC + TEE attestation, AVS-verified | no |
| vlayer | no longer a fit: docs now cover "Vouch" (user-login web proofs) and a Social Data API; dev SDK's last release is a Nov 2025 nightly | user-login flows | historically TLSNotary plus RISC0 | not confirmed |

Reclaim's internal Groth16 proofs (zk-symmetric-crypto, chacha20 / AES) only prove decryption to the
attestor. They do not prove the final claim, so they are not a useful thing to send to zkVerify.

**Chosen: Reclaim zkFetch.**
- It runs in Node inside the agent, hides the GitHub token, and pins `merged:true`, the PR number and the merger login with regex matches.
- Its `context` field binds the bounty ID and payee into the signed claim, so a proof can't be replayed for another bounty.
- It is the most active Node SDK of the five; Primus is the drop-in fallback with the same trust model.

## 5. Fallback design (recommended as the primary design)

zkTLS proofs cannot go to zkVerify directly, so:

1. **Agent verifies zkTLS off-chain** with Reclaim `verifyProof`, then checks the extracted fields against the bounty.
2. **Mandate circuit** (Circom, Groth16, BN254, snarkjs) proves amount ≤ cap, spent + amount ≤ budget,
   payee in the allowlist Merkle root, and now < expiry. Its public inputs also include **claimHash = the Reclaim
   claim `identifier`** (split into two field elements) plus the bounty ID. One proof binds "this delivered work"
   to "this payout is in mandate".
3. The mandate proof goes **to zkVerify via Kurier**, aggregated to Base Sepolia.
4. **BountyVault.release()** checks:
   - `verifyProofAggregation` on the zkVerify proxy for a leaf rebuilt from its own stored mandate and the claimHash;
   - `ecrecover(claimHash-derived digest, attestor signature)` equals a whitelisted Reclaim attestor;
   - on-chain `spent` and expiry.
   Only then does it transfer test USDC.
5. The receipt page shows the Reclaim claim, the zkVerify tx and aggregation IDs, and the release tx.

Rejected alternatives:
- **ECDSA-in-Circom** (about 1.5M constraints, a 2^21 ptau, minutes and GBs of RAM per proof): too heavy for an always-on host.
- **RISC0 / SP1 guest re-verifying the signature**: adds Rust and heavy proving, which is an architecture change.

## 6. Mandate reuse

- `PermissionMirror.PermissionScope` (`maxPositionSizeUsdc`, `maxDailySpendUsdc`, `expiry`) maps to the vault's
  per-payout cap, total budget and expiry. The protocol bitmask is replaced by a payee allowlist.
- `src/lib/underwriting.ts` ordered checks are ported to `packages/shared/src/mandate-check.ts`, the reference semantics
  that the circuit and contract must match.
- Gap: Mandate tracks cumulative spend off-chain only; BountyVault tracks `spent` on-chain.
